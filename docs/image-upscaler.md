# Image Upscaler implementation and local review

## Diagnosis

The exact reported error was generated by the old image rate-limit helper, not by an AI provider. Commit `3381e19` configured image limits to fail closed in production. Missing or unreachable Redis returned `unavailable`, which the helper translated into HTTP 503 with “Image processing is temporarily unavailable. Please try again shortly.” Commit `f0dcb00`, already present in this checkout, replaced that behavior with bounded in-memory limits. The existing Redis fallback regression test passes. Production logs and the deployed revision were not available for inspection; confirming that the deployed application contains this earlier fix remains a deployment check.

Separately, the original upscaler had no inference engine, model assets, or model API credentials. It authorized a credit operation, enlarged the image through `CanvasRenderingContext2D.drawImage`, and submitted a client completion. Repairing the rate limiter alone would therefore only restore interpolation.

## Processing and licensing

- Separate learned 2× and 4× RDN models from `@upscalerjs/esrgan-slim@1.0.0`; no cascading resize or CSS enlargement. This small model was chosen over a large Real-ESRGAN network for CPU browser feasibility.
- The publisher distributes these models under [MIT](https://github.com/thekevinscott/UpscalerJS/blob/v1.0.0/models/esrgan-slim/LICENSE), allowing commercial use with its notices retained. The installed model package README and LICENSE were inspected.
- TensorFlow.js 4.11.0 core/WASM use Apache-2.0; [Layers uses Apache-2.0 and MIT](https://github.com/tensorflow/tfjs/blob/tfjs-v4.11.0/tfjs-layers/LICENSE). Full license notices are retained in `public/upscaler-notices` and copied beside generated model assets.
- A dedicated Web Worker performs single-thread WASM inference. No WebGPU, SharedArrayBuffer, cross-origin isolation, inference server, API key, paid provider, or external service registration is required. Only authentication/accounting use the existing SavDown API.
- Inputs stay on the device. Output is always a real PNG. RGB is inferred; alpha is preserved separately using nearest source alpha samples. Alpha is not AI-enhanced. The browser handles EXIF orientation before inference.
- Model weights and runtime binaries are copied from pinned npm packages during predev/prebuild. The manifest pins sizes and SHA-256 hashes; build preparation and browser loading verify them. Browser Cache Storage is optional, and corrupt entries are evicted. Only one scale model stays resident in each worker.

## Limits and cost

- Input formats: still JPEG/JPG, PNG and WebP, up to 5 MiB. Animated WebP is rejected.
- Maximum output: 4,194,304 pixels. 2× permits up to 1,048,576 source pixels; 4× permits up to 262,144 source pixels. Maximum input side: 2048 pixels.
- Compressed headers are checked before preview/decode, then decoded dimensions are checked again in the worker. Invalid, mismatched and oversized inputs fail without an inference or credit debit.
- Inference uses 32×32 source cores with a 16-pixel overlap halo. Tensors are disposed after each tile; bitmaps, object URLs and workers are released when appropriate. The full output RGBA surface alone may use 16 MiB, with additional source, WASM, model activation and PNG encoding memory. This is not a hard browser-process memory cap. Low-memory devices can still reject allocation; reduce input size if necessary.
- Model assets plus all WASM variants total approximately 2 MiB for one scale, in addition to the bundled application JavaScript. Subsequent matching images reuse the model; reloads can use verified cached bytes.
- Progress is measured by completed tiles. Runtime/model initialization and PNG encoding are honestly indeterminate. There is a 60-second per-asset download timeout and a 120-second worker inactivity timeout, reset by tile progress. There is no promised total completion time. Large jobs can take minutes, especially on mobile.
- No inference fee, paid API, GPU service, or additional hosted infrastructure is introduced. Existing hosting bandwidth, authentication and database usage still use the site's normal infrastructure and quotas. This cannot guarantee an unlimited zero-cost Vercel bill.
- Existing `JOB_COST.imageTool` remains unchanged (currently 1 credit). Authorization creates a processing record without spending. Only a verified worker output causes the UI to send completion. The existing atomic credit ledger handles concurrent duplicate spends. The API acknowledges a previously completed operation before balance preflight, so retrying a lost response still works after spending the last credit.
- Completion failure retains the generated blob and operation key for accounting retry. An inference failure records failure without spending and uses a fresh operation key for a subsequent attempt. A client receipt is not cryptographic attestation: as with the existing browser-tools architecture, the server cannot prove a modified browser executed the model. It authenticates ownership and validates operation state and receipt bounds.

## Local verification

Focused Vitest command:

```powershell
npm test -- src/lib/upscaler/input.test.ts src/app/api/tools/image/image-upscaler/route.test.ts src/lib/imageRateLimit.test.ts src/lib/imageService.test.ts src/app/api/tools/image/route.test.ts src/lib/credit-reconciliation.test.ts
```

Result: 28 tests passed across 6 files. Coverage includes real JPEG/PNG/lossy and lossless WebP headers, bad MIME/content, oversized images/files, scale bounds, configured credit cost, authorization without spending, failed inference without spending, authenticated ownership, receipt validation, duplicate completion with exhausted balance, changed balance, malformed/oversized request bodies, Redis fallback, existing image processing and credit reconciliation. Accounting tests mock authentication/database boundaries; no production accounts were charged.

`npx tsc --noEmit` and targeted Next lint passed during implementation. The optimized production build passed, with existing HEIC dynamic-require and unrelated lint warnings. Static page generation also logged an invalid local `DATABASE_URL` protocol, so actual database billing could not be verified locally. Environment files were not changed.

The generated Next file-tracing manifests for the tool page and upscaler API contain zero TensorFlow/model package files, confirming that inference packages and weights are not being placed in those server functions. Generated model/runtime files remain public static assets.

Initial real headless Chrome UI run (real WASM/model inference, mocked sign-in and accounting):

| Mode | Input | Generated PNG | Bytes | Time including UI work |
| --- | --- | --- | --- | --- |
| 2× | 45×37 graphic | 90×74 | 16,061 | 8.9 seconds, cold worker |
| 4× | 45×37 graphic | 180×148 | 39,824 | 1.5 seconds, warm runtime |

Actual downloaded files were decoded with Sharp, checked for PNG format and dimensions, and visually inspected in the rendered page. Mean per-channel absolute difference from ordinary Lanczos resizing was 8.69/255 (2×) and 7.50/255 (4×), confirming a different processing path; difference alone is not a universal quality metric. Model enhancement can introduce artifacts and does not reconstruct provably original detail.

Production-bundle Chrome verification also passed:

- JPEG photograph: 64×64 to 128×128, 41,887-byte PNG, approximately 2.5 seconds cold.
- WebP portrait crop: 48×64 to 192×256, 63,070-byte PNG, approximately 1.9 seconds.
- Transparent PNG: 33×25 to 132×100; output alpha exactly matches source 0/128/255 samples across all output pixels.
- JPEG EXIF orientation 6: 40×25 encoded source becomes a correctly oriented 50×80 PNG at 2×.
- Real measured progress samples included 25%, 50%, and 75%; initialization/encoding remained indeterminate.
- Seven model/runtime assets cached; page reload and another 2× output required zero asset requests. Deliberately truncating cached weights caused exactly one replacement request and a successful verified output.
- SVG, corrupt PNG and an oversized-dimension PNG produced specific errors without completion requests.
- A simulated accounting failure retained the output; retry neither reauthorized nor fetched assets again.
- A missing WASM asset produced a real deployment-asset error without a completion, followed by a successful retry after the asset became available.
- Desktop light and 390-pixel mobile dark views were inspected. Mobile width did not overflow. This uses Chrome emulation, not a physical phone.
- Maximum 4× boundary: a 512×512 JPEG generated a decoded 2048×2048 PNG of 3,908,824 bytes in 80.4 seconds. A 100 ms main-page heartbeat ran 803 times during processing, confirming the interface stayed responsive. Cancellation of a second boundary job generated one failure request and no additional completion request.
- Final production build exited 0. Final browser regression verified that a 513×512 input remains previewable, 4× is rejected before authorization, and switching to 2× works. It also verified fresh operation keys after authorization rejection, the same operation key after an accounting failure, and a decoded 26×22 PNG from a 13×11 source.

The test photograph was NASA's Eileen Collins portrait (`skimage/data/astronaut.png` from scikit-image v0.25.2). Against a higher-resolution reference, the 2× model scored 22.61 dB PSNR versus 21.08 dB for Lanczos. The 4× portrait crop scored 26.98 dB versus 27.65 dB for Lanczos and had visible texture artifacts. Therefore the small learned model improves some detail but is not universally superior to interpolation; 4× is a stronger speed/quality compromise. A side-by-side comparison was saved for review. These metrics compare the actual generated pixels, not API success responses.
